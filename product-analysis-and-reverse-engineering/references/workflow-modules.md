# Workflow Modules

## Journey

1. Define the evidence range and inaccessible areas.
2. Reconstruct the chronological path from entry to outcome.
3. For every step, record user goal, user action, page feedback, decision, state/object change, emotion, friction, and evidence.
4. Identify continue, modify, choose-alternative, return, interrupt, fail, and recover controls.
5. Draw three lanes: User, Product Interface, System Result.
6. Use diamonds for evidenced decisions and label branch conditions.
7. End with the three highest-value experience issues and product opportunities.

## Actors

1. Identify visible actors without assuming a fixed count.
2. Record when each actor joins, who triggers it, what it replaces, what it hands off, and whether it can be called again.
3. Inspect six input classes: current user input, long-term user information, project/global context, upstream output, platform knowledge/assets, runtime/tool results.
4. Summarize only observable functional judgments, not private reasoning.
5. Name tools functionally when official names are not visible and label them non-official.
6. Inspect five output classes: user reply, UI components, business/visual assets, context/state writes, downstream tasks.
7. Build producer-consumer and invalidation relationships.

## Behavior

1. Select one evidenced Agent or automation role.
2. Establish scope, trigger, ownership, exclusions, stop conditions, automatic continuation, confirmation gates, and re-entry.
3. Build input, output, tool, context, and state-machine contracts.
4. Convert evidence into fact, inference, recommendation, and unknown rules.
5. Write a functional-equivalent behavior prompt using observable semantics.
6. Trace every important rule to evidence.
7. Test complete input, missing input, local modification, tool failure, interruption, duplicate request, and state conflict.

## Architecture

1. Identify functional domains from the user's perspective.
2. Trace user interaction, control, tool, data/context, and artifact flows.
3. Build only applicable layers.
4. Separate current architecture, inferred mechanisms, and recommended design.
5. Model context as structured domains rather than one undifferentiated store.
6. Distinguish project data, reusable knowledge, public assets, private assets, and runtime state.
7. Describe required infrastructure capabilities before possible technologies.
8. Build entity, ER, sequence, panorama, As-Is, To-Be, risk, and traceability views at deep depth.

## Packaging

1. Preserve source artifacts.
2. Create corrected scene folders and sequence-based copies.
3. Generate an evidence registry and gallery.
4. Include Markdown, HTML, Mermaid source, CSV, and supporting evidence as applicable.
5. Validate links and evidence IDs.
6. Package with a manifest and report omitted or inaccessible evidence.
